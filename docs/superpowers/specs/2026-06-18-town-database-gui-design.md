# Town database GUI: design spec

Date: 2026-06-18
Status: ready for implementation planning

## Overview

Grow a new `/browse/` section on marbleheaddata.org that is a database GUI for the underlying town data. SaaS-admin shape, not Tableau-dashboard. Tables as browseable entities, list views with filter/sort/search, detail views per row, cross-references between entities.

Backed by a SQLite file salvaged from PR #849, extended over time with more tables. The existing editorial pages (`/topics/`, `/charts/`, `/2026-override/`, `/the-debate/`) stay intact. They become "saved views" or "interpretation layers" on top of the data; the new `/browse/` section is where you query the raw data directly through a UI.

The motivating frame, in the user's words: "all the town data is a db, and this is the web GUI for it, like you'd expect for any SaaS." Not Stripe-the-dashboard. Stripe-the-admin-panel.

## Goals

- A consistent `/browse/` shell with left-nav of entities, breadcrumb, per-entity search.
- List views for the four Phase 1 entities (Vendor payments, Budget lines, Meetings, Topics), each filterable and sortable, sub-second on a typical viewer's device.
- Detail views per row, linking to existing editorial pages where they exist (each meeting links to its existing transcript page; each topic links to its existing topic-feed page).
- A SQLite-backed data layer with primary-source citations on every table (the `_meta` pattern from PR #849).
- Build pipeline that regenerates the SQLite on every Jekyll build (or on a separate cron), keeping the GUI fresh as new data lands.

## Non-goals (Phase 1)

- **No SQL editor surface.** PR #849's `/data/lab/` page is explicitly NOT shipped as part of this work. SaaS admin GUIs hide SQL under nice UI; we're following that convention.
- **No live data via Workers / D1.** All four Phase 1 entities are append-only or slowly-mutating; static SQLite + client-side queries is sufficient.
- **No migration of `/checkbook/` or `/explore/` to query the SQLite.** Those pages keep their current bespoke JSON loaders for now. The `/browse/` shell links to them. Migration is a future phase.
- **No authentication / user state.** No saved filters, no alerts, no per-user dashboards.
- **No global cross-entity search.** Per-entity search only in Phase 1; global cmd+K is Phase 2.
- **No new entities beyond the four.** Officials, Source documents, Charts, and Peer towns are not in Phase 1.

## Architecture

Two layers:

```
                    +-----------------------------+
   GUI surface  →   |  /browse/ Jekyll pages      |
                    |  (list, detail, search)     |
                    +---------------+-------------+
                                    |
                                    | reads via sql.js
                                    v
                    +-----------------------------+
   Data backend →   |  marbleheaddata.sqlite      |
                    |  (built from data/ JSON+CSV)|
                    +---------------+-------------+
                                    ^
                                    | builds via Python
                    +-----------------------------+
                    |  scripts/build_sqlite_db.py |
                    +-----------------------------+
```

### Data backend

Single `marbleheaddata.sqlite` file lives at `assets/data/marbleheaddata.sqlite` (path from PR #849). Generated by `scripts/build_sqlite_db.py` from the raw JSON/CSV files in `data/`. Every table has a row in the `_meta` table with its primary-source citation.

In Phase 1 the SQLite holds (at minimum) the four Phase 1 entities plus the existing eight tables from PR #849. PR #849's salvaged tables (`ma_overrides`, `ma_towns_fy26`, `marblehead_levy`, etc.) stay in the file even though they aren't surfaced in the Phase 1 left nav; they remain queryable for power users via the downloadable file.

Loaded into the browser via [sql.js](https://github.com/sql-js/sql.js) (SQLite compiled to WASM). The file is ~1.4 MB at PR #849 baseline; Phase 1 additions push it to an estimated 3-5 MB. The full file is fetched once on first page load, cached by the browser, queried client-side.

### GUI surface

Static Jekyll pages under `/browse/` that load the SQLite, render list views and detail views with JS. The shell (left nav, breadcrumb, per-entity search) is a Jekyll include reused across pages. Each entity has:

- A list-view page (`/browse/<entity>/`)
- A detail-view route. Either a generated Jekyll page per row OR a client-rendered detail pane on the same page; chosen per entity below.

JavaScript loads `marbleheaddata.sqlite` via sql.js on first navigation to `/browse/`, caches the database object across in-page transitions, and runs queries for list/detail/search interactions.

## GUI shell

Common chrome on every `/browse/*` page:

```
┌──────────────────────────────────────────────────────────┐
│  Site header (existing nav)                              │
├────────────────┬─────────────────────────────────────────┤
│                │  Browse > Vendor payments               │
│  BROWSE        ├─────────────────────────────────────────┤
│                │                                         │
│  ◆ Vendors     │  [search this list]   [filter] [sort]   │
│  ◆ Budget      │                                         │
│  ◆ Meetings    │  vendor          dept         amount    │
│  ◆ Topics      │  ─────────────────────────────────────  │
│                │  Acme Corp       Schools     $44,512    │
│  Power user    │  ...                                    │
│  Download .db  │                                         │
│                │                                         │
└────────────────┴─────────────────────────────────────────┘
```

Components:

- **Left nav.** Static list of the four Phase 1 entities, each linking to its list-view page. Below the nav, a "Power user: download the database" link to the salvaged SQLite file (PR #849's affordance, kept).
- **Breadcrumb.** `Browse > <entity>` on list pages, `Browse > <entity> > <row title>` on detail pages.
- **Per-entity search bar.** Top of each list view. Filters the visible rows client-side using sql.js full-text matching or a `LIKE %term%` query over indexed columns. No global search in Phase 1.
- **Filter/sort controls.** Per-entity, defined in each entity's section below.

Responsive behavior: on viewports below 800px, the left nav collapses into a top-of-page hamburger or sticky entity-switcher. Mobile gets the same data and the same interactions; the chrome rearranges.

## Phase 1 entities

### Vendor payments

The financial transaction log of the town.

**Source:** `data/checkbook_FY26_2026-06-09.csv` (currently ~thousands of rows) and any earlier-year checkbook CSVs that already exist or get added. The `scripts/build_sqlite_db.py` build pipeline ingests these into a `vendor_payments` table.

**Schema (proposed):**

```sql
CREATE TABLE vendor_payments (
  id INTEGER PRIMARY KEY,
  payment_date TEXT,             -- ISO date
  fiscal_year TEXT,              -- e.g. "FY26"
  vendor TEXT,
  department TEXT,
  category TEXT,                 -- if available
  amount REAL,
  fund TEXT,                     -- general fund, water, sewer, etc.
  source_file TEXT               -- which CSV this row came from
);
CREATE INDEX vp_vendor ON vendor_payments(vendor);
CREATE INDEX vp_department ON vendor_payments(department);
CREATE INDEX vp_date ON vendor_payments(payment_date);
```

**List view (`/browse/vendors/`):** sortable table with columns `date | vendor | department | amount`. Filter chips at the top for fiscal year (multi-select), department (multi-select), fund (single-select). Search bar matches against `vendor` and `department`. Default sort: date descending. Default page size: 100 rows; "load more" button extends the view.

**Detail view:** clicking a vendor name (not a row) opens `/browse/vendors/<slugified-vendor>/`, which shows all payments to that vendor across all years, plus a summary (total paid, departments, payment count, first/last date). Vendor names with no slug-collision issues; collisions handled by appending the row id.

**Cross-references:** clicking a department in any payment row navigates to `/browse/budget/?dept=<department>` (the Budget lines list filtered to that department).

**Relationship to existing `/checkbook/`:** `/checkbook/` keeps its current implementation and remains the primary "drill-down with charts" surface. `/browse/vendors/` is the table-shaped sibling. Both link to each other; eventually `/checkbook/` could migrate to query the same SQLite, but not in Phase 1.

### Budget lines

The town's appropriated budget, broken out by department and line item.

**Source:** `data/FY26_budget_summary.json`, `data/budget_FY26_by_fund.json`, `data/budget_drill_FY26.json`, plus equivalent files from prior years that already exist or get added (likely `budget_*_FY25.json`, etc.). The build pipeline normalizes these into a single long-form table.

**Schema (proposed):**

```sql
CREATE TABLE budget_lines (
  id INTEGER PRIMARY KEY,
  fiscal_year TEXT,
  department TEXT,               -- "Schools", "Fire", etc.
  line_item TEXT,                -- e.g. "Health Insurance Transfer"
  fund TEXT,
  amount REAL,
  budget_phase TEXT              -- "adopted", "proposed", "revised"
);
CREATE INDEX bl_dept ON budget_lines(department);
CREATE INDEX bl_fy ON budget_lines(fiscal_year);
```

**List view (`/browse/budget/`):** sortable table with `fiscal year | department | line item | amount`. Filter chips for fiscal year, department, fund. Search matches against `line_item` and `department`. Default sort: fiscal year descending then department ascending.

**Detail view:** clicking a department name navigates to `/browse/budget/<department>/`, which shows all line items in that department across all fiscal years (a small spreadsheet view). Year-over-year trend chart at the top (optional, low priority for Phase 1).

**Cross-references:** each row links sideways to `/browse/vendors/?dept=<department>` (vendors paid by that department).

### Meetings

Every Select Board, School Committee, Finance Committee, and other-board meeting the site has a record of.

**Source:** `_transcripts/*.md` (232 files at time of writing, growing weekly). Also `data/minutes_catalog.csv` (the 331-row minutes catalog from PR #849). The build pipeline scans the front-matter and contents of every transcript markdown file, extracts metadata, and writes a `meetings` row per file.

**Schema (proposed):**

```sql
CREATE TABLE meetings (
  id INTEGER PRIMARY KEY,
  meeting_date TEXT,             -- ISO date
  board TEXT,                    -- "select-board", "school-committee", "fincom", etc.
  title TEXT,
  slug TEXT,                     -- existing transcript filename slug
  has_transcript INTEGER,        -- 1 if a transcript file exists in _transcripts/
  has_digest INTEGER,            -- 1 if a meeting-digest summary exists
  topic_tags TEXT,               -- comma-separated topic slugs (FK to topics.slug)
  url TEXT                       -- /transcripts/<slug>/ or /meeting-digest/<slug>/
);
CREATE INDEX m_date ON meetings(meeting_date);
CREATE INDEX m_board ON meetings(board);
```

**List view (`/browse/meetings/`):** sortable table with `date | board | title`. Filter chips for board (multi-select), year (single-select), has-transcript (toggle). Search matches against `title`. Default sort: date descending. Pagination at 50 rows per page.

**Detail view:** the existing transcript page (`/transcripts/<slug>/` or `/meeting-digest/<slug>/`). No new detail page is built; the GUI links out. The list-view row click opens the existing page in the same tab.

**Cross-references:** clicking a topic tag navigates to `/browse/topics/<slug>/` (the topic detail view).

### Topics

The 13 existing topic pages, treated as rows.

**Source:** the existing `topics/*.html` files. Each has front-matter with `title`, `permalink`, `topic_slug`. The build pipeline scans these and writes a `topics` row per file. The `topic_seeds.json` data file may also feed in additional metadata (descriptions, related charts).

**Schema (proposed):**

```sql
CREATE TABLE topics (
  slug TEXT PRIMARY KEY,
  title TEXT,
  description TEXT,
  page_url TEXT,                 -- /topics/<slug>/
  meeting_count INTEGER          -- denormalized count of meetings tagged with this topic
);
```

**List view (`/browse/topics/`):** simple table with `topic | description | # meetings tagged`. No filter chips; search matches against title and description. Default sort: alphabetical. The list is short (13 rows) so no pagination.

**Detail view:** the existing `/topics/<slug>/` page is the detail view. No new page built. The existing topic-feed include already shows the meeting feed for that topic; the `/browse/topics/` list view just provides another path in.

**Cross-references:** the existing topic page already cross-links to its meeting feed; that's preserved.

## URL structure

```
/browse/                              index page; brief intro, entity cards
/browse/vendors/                      list view
/browse/vendors/<slug>/               detail view (new page, client-rendered)
/browse/budget/                       list view
/browse/budget/<dept>/                detail view (new page, client-rendered)
/browse/meetings/                     list view
                                      (detail view = existing /transcripts/<slug>/)
/browse/topics/                       list view
                                      (detail view = existing /topics/<slug>/)
```

The `<slug>` and `<dept>` detail pages are single Jekyll pages that read the slug from the URL via JS and query the SQLite for matching rows. No pre-generation of one Jekyll page per vendor (there are too many vendors; would bloat the build).

## Search (Phase 1)

Per-entity, in each list view's header. Implementation: the search box's value populates a `LIKE %term%` query against the entity's searchable columns. Debounced at 200ms. Sub-second for the largest table (vendor payments).

Out of scope for Phase 1: global cmd+K search across all entities; fuzzy/typo-tolerant search; ranked relevance. Phase 2 adds these.

## Implementation phasing

The work decomposes into three sub-projects, each with its own implementation plan and PR:

### Phase 1a: Data layer salvage and extension

- Cherry-pick the data layer from PR #849: `scripts/build_sqlite_db.py`, the build artifact `assets/data/marbleheaddata.sqlite`, the `_meta` table pattern. Do NOT cherry-pick `assets/data-lab.js`, `data/lab.html`, or the modified `data/index.html` (the Data Lab tile).
- Extend `scripts/build_sqlite_db.py` to also ingest:
  - `data/checkbook_FY26_2026-06-09.csv` (and prior years if available) → `vendor_payments`
  - The FY26 budget JSONs → `budget_lines`
  - `_transcripts/*.md` + `data/minutes_catalog.csv` → `meetings`
  - `topics/*.html` front-matter → `topics`
- Add `_meta` rows for each new table.
- Verify the SQLite still opens cleanly in DB Browser, `sqlite3` CLI, Python, R.
- Close PR #849 in favor of this one. PR description explicitly says: salvaged from #849, the SQL editor surface is intentionally dropped.

**Deliverable:** a PR that ships the SQLite file with all Phase 1 tables, no UI changes yet.

### Phase 1b: `/browse/` shell + list views

- New Jekyll layout for `/browse/*` pages (shell with left nav, breadcrumb).
- `assets/browse.js` (or similar): sql.js loader, common query helpers, list-view rendering, search debouncing.
- Four list-view pages: `/browse/vendors/`, `/browse/budget/`, `/browse/meetings/`, `/browse/topics/`. Each loads the SQLite, queries its entity table, renders a table with filter chips and search box.
- `/browse/` index page with brief intro and four entity cards.

**Deliverable:** a PR that makes the four list views functional, no detail views yet (links from rows go to existing pages where they exist, or are inert for vendors/budget).

### Phase 1c: detail views and cross-references

- `/browse/vendors/<slug>/` and `/browse/budget/<dept>/` detail pages.
- Cross-reference links wired up (vendor → department in budget, meeting → topic, etc.).
- Final polish: empty-state messaging, loading spinners while sql.js initializes, mobile breakpoints.

**Deliverable:** a PR completing the Phase 1 GUI.

The three phases are independent enough that they can be reviewed and merged sequentially without blocking each other.

## Out of scope (phase boundaries)

Phase 2 candidates, not part of this spec:

- Global cmd+K search across all entities.
- New entities: Officials & committees, Source documents, Charts as entities, Peer towns (Town Explorer is its own surface).
- Migrating `/checkbook/` and `/explore/` to query the SQLite (currently bespoke JSON loaders).
- Live data via Cloudflare Workers / D1 (current static SQLite is sufficient).
- Authentication, saved filters, alerts, user state.
- Inline charts / sparklines in list views.

## Open questions for implementation

1. **Search performance on vendor_payments.** Tens of thousands of rows on a `LIKE %term%` query with sql.js: needs benchmarking. If too slow, the implementation may need an FTS5 virtual table for vendor and department columns. The Phase 1b plan should include a benchmarking step before committing to the architecture.

2. **SQLite file size budget.** If Phase 1 tables push the SQLite past ~10 MB, the first-page-load fetch becomes a real concern on slow connections. Mitigation options if it bloats: drop the salvaged PR #849 tables that aren't surfaced in the GUI yet (they can come back when their list views are built), or paginate vendor_payments by fiscal year into separate files.

3. **Build cadence.** PR #849's pipeline runs once at PR-merge time. For the Meetings table to stay fresh as new transcripts land weekly, the SQLite needs to rebuild on every Jekyll build or on a separate cron. The Phase 1a plan picks one.

4. **Slug collisions on vendor detail pages.** Vendors with the same normalized name (e.g. "ABC Inc" and "ABC, Inc.") would collide on `/browse/vendors/<slug>/`. The Phase 1c plan picks a disambiguation rule (numeric suffix, or include vendor id in URL).
